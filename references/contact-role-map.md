# Contact Strategy · 联系策略（V1.1）

**回答两个问题：找谁 + 什么时机找。**

**本文件只输出岗位角色，不输出具体人名。**

---

## 一、硬性约束（不可绕过）

| # | 约束 |
|---|---|
| 1 | **默认只推荐岗位角色**，并且**必须给出该岗位所属的主体与职能单位** —— 输出结构为 `主体（法人 / 业务主体）→ 职能单位 → 目标岗位`（见第三节） |
| 2 | **禁止生成**具体人名、电话、邮箱、微信号、社交账号 |
| 3 | 仅当**公开来源确实查到**真人信息时，才可展示 `Name + Position + Source` |
| 4 | **证据来源白名单**（**只约束"展示真人"这件事**）：企业官网、政府公示文件、招投标公告、上市公司公告、官方媒体报道。**该白名单不适用于第三节情况 C 的「建议检索路径」** —— 路径只是告诉业务员"去哪里找这个人"，**不构成本卡可引用的证据**，也不得据路径推断出任何人名 |
| 5 | 查不到 → 输出 `No verified contact found`。**不得用"可能是张工"这类表述** |
| 6 | **`No verified contact found` 不是终点** —— 必须同时输出第三节情况 C 的「**建议检索路径**」，回答"下一步去哪里找这个角色" |
| 7 | 不得从询盘签名栏推断出联系方式以外的信息（签名栏本身可标注为「客户自述」） |
| 8 | **职能单位（部门 / 中心 / 事业部 / 区域总部等）必须有公开来源支撑**；无来源时**只输出 `主体 → 岗位`（二段式）**，**不得为凑齐三段结构而推测部门名称** |
| 9 | **主体必须写"法人 / 业务主体"口径** —— 品牌名 ≠ 登记主体时（如品牌与实际经营主体分属不同法律主体），须写实际主体，并在第三节的说明里注明口径来源 |

> **为什么严格**：LLM 极易顺着"帮我找联系人"编出一个看起来合理的姓名，销售会真的去打。既浪费时间，也可能触及个人信息合规问题。

### Evidence 要求（遵循 `evidence-policy.md`）

| 结论 | 类型 | 要求 |
|---|---|---|
| 岗位角色（由客户类型 / Path 推导） | **INFERENCE** | 必须有 `Reason`（哪条判据推出该类型） |
| `Name + Position + Source`（公开来源查到真人） | **FACT** | 必须有 `Source` |
| 查不到真人 | **UNKNOWN · searched** | 输出 `No verified contact found`，**不得补全** |
| 客户类型 / Path 为 `Unconfirmed` | **UNKNOWN** | 不推荐其他岗位，`Next Action` 为"确认客户类型" |

## 二、Path / 客户类型 → 推荐联系岗位序列

按顺序尝试。**第一位是首选接触点。**

### End-user Path

#### 1. 终端业主（工厂）

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **环保负责人 / 安环部负责人** | 首选。技术认可的实际把关人，通常也是询盘发起方 |
| ② | **技术总工 / 生产技术负责人** | 技术方案需要上升到生产线层面时 |
| ③ | 设备科 / 采购经理 | 进入商务阶段后 |
| ④ | 总经理 / 老板 | 中小民企可跳过前几层直达；大企业不宜越级 |

#### 1b. 多厂区集团（End-user · 集团型）

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **集团环保 / EHS 负责人** | 首选。确认目标厂区与集团层面的项目机制 |
| ② | **优先厂区（Priority Site）环保负责人** | 落地接触点。厂区级事实必须由厂区确认 |
| ③ | 集团技术 / 运营负责人 | 需要上升到生产运营层面时 |

**说明**：集团有 N 个厂区 ≠ 每个厂区都有需求。**必须区分集团级与厂区级**，优先接触 `Priority Site` 对应厂区。

### Partner Path

#### 2. 环保工程公司（EPC）

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **工艺工程师 / 技术工程师** | 首选。负责选型，决定用谁的电极 |
| ② | 项目经理 | 项目已中标、进入执行期 |
| ③ | 采购 | 进入商务阶段后 |
| ④ | 技术总监 / 总工 | 技术争议或需要厂家背书时 |

#### 2b. 系统集成商（Integrator）

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **工艺 / 技术负责人** | 首选。判断组合是否需要补齐 |
| ② | **产品经理** | 评估产品线的互补性 |
| ③ | 采购 / 供应链 | 进入商务阶段后 |

**说明**：切入角度是**组合补齐**而非替代其自有工艺。若存在竞争关系，先明确边界。

#### 3. 设计院

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **工艺设计师（水处理专业）** | 首选。决定设备选型规格 |
| ② | 专业负责人 / 主任工程师 | 需要将品牌写入设备选型清单时 |
| ③ | 项目负责人 | 整体进度协调 |

**说明**：不直接采购，但决定了后面所有供应商的规格。**最高杠杆的接触点。**

#### 4. 科研院所 / 高校

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **课题负责人（老师 / 教授）** | 首选。决定买不买、买多少 |
| ② | 博士生 / 研究生（实验执行人） | 对接技术细节与规格 |
| ③ | 实验室采购 / 设备处 | 走流程、开票 |

#### 5. 贸易商 / 中间商 / 分销代理

| 顺序 | 岗位 | 何时找 |
|---|---|---|
| ① | **负责人 / 总经理** | 通常一人决策 |
| ② | 业务 / 采购负责人 | 需要了解渠道覆盖与终端结构时 |

**说明**：**必须先索要终端信息**，确认前不投入技术支持资源。

### Undetermined

#### 6. Unconfirmed（类型未确认）

| 顺序 | 岗位 |
|---|---|
| ① | 询盘发起人（保持现有接触点，不主动升级） |

**说明**：类型未确认前不推荐其他岗位。应先通过提问确认客户类型与需求性质。

## 三、输出格式

> **V1.1.6 起统一为「主体 →（职能单位 →）岗位」结构。**
> 目的：解决"4 张同类型客户的联系人字段逐字相同"的问题 —— 岗位序列本身按类型固定，**区分度必须由主体与职能单位提供**。

### 情况 A：**三段式**（能确认职能单位时 · 首选）

```
Recommended Contact Role: {主体（法人 / 业务主体）} → {职能单位} → {目标岗位}
  Source: {职能单位的公开来源}
```

**示例**：`某工业水处理集团（印度）→ 技术中心 → 工艺技术负责人`

### 情况 A′：**二段式**（无法确认职能单位时 · 允许退化）

```
Recommended Contact Role: {主体（法人 / 业务主体）} → {目标岗位}
  说明：未能从公开来源确认职能单位 → 按第一节约束 8 退化为二段式，不推测部门名称
```

> **退化是正确输出，不是缺陷。** 为凑齐三段而编一个部门名，会让业务员找错部门。

### 情况 B：公开来源查到真人

```
Recommended Contact Role: {主体} → {职能单位} → {目标岗位}
  Name: {姓名}
  Position: {职位}
  Source: {URL 或来源全名}
```

### 情况 B′：**部分具名**（存在具名，但**不是**当前 Primary Contact 岗位 · **V1.1.6 新增**）

```
Recommended Contact Role: {主体} → {职能单位} → {目标岗位}
  Primary Contact: `No verified contact found`（目标岗位无公开可核实的具名）
  Known / Escalation Contact（**非目标岗位**）:
    Name: {姓名} ｜ Position: {职位；官网未载明职务时如实写"未载明职务"} ｜ Source: {允许来源}
  说明：该具名人员**不构成 Primary Contact 已找到**；不得据此推断其负责当前技术项目
```

| # | 规则 |
|---|---|
| 1 | **可以**展示该具名联系人及其来源（仍须符合第一节约束 3 / 4 的来源白名单） |
| 2 | **不得**把 Primary Contact 标记为「已找到」 |
| 3 | Primary Contact **仍须**输出目标岗位 ＋ `No verified contact found`；**情况 C 的「建议检索路径」同样适用** |
| 4 | 已具名但非目标岗位的人 → 标注为 **Secondary / Escalation / Known Contact**，不得混入 Primary |
| 5 | **不得**因为存在一个公开姓名，就推断其能负责当前的技术项目 |
| 6 | **不新增 Internal Key / 字段** —— 全部内容写入既有的 `关键联系人 Contact` 字段内 |

> **为什么单列**：实测出现过「官网只公开一位非技术岗位的联络人，而目标技术岗位无具名」的情形。
> 既不能因此宣称「已找到联系人」，也不该把这条公开信息丢掉。

### 情况 B′ 写法补充：联系人字段四要素（**2026-10-21 新增 · 实测样例**）

> **背景**：某客户卡把「官方角色信箱 / 具名媒体联系人 / 具名高管旁证」混写一段 ⇒
> 下游 outreach 执行器把**具名媒体联系人的个人邮箱**当作通用渠道且排在首位（误判）。
> 本补充**只约束 `关键联系人 Contact` 字段的写法**，不新增 Internal Key、不改任何判定。

卡面联系人字段凡同时出现多类信息，**必须用以下四个标签分段明示**（全角括注即可）：

| 要素 | 标签 | 写法要求 |
|---|---|---|
| ① 官方邮箱证据 | `官方渠道` | 只列**角色信箱**（info@/sales@/office@ 等部门口径）＋ 来源；每条须可追溯到来源页 |
| ② 具名联系人 | `具名（Verified）` | 姓名＋职务＋来源；**职务照录来源原文**，不得概括升格 |
| ③ 岗位相关性 | `目标岗 / 非目标岗` | 每个具名人标明是否为目标岗位（非目标岗 → 标 `Known / Escalation`，不混入 Primary） |
| ④ 决策权口径 | `决策权：未知` | **一律写 `未知`**，不得从职务推测采购决策权（媒体/市场联系人须标注「不承担采购职能」类原文口径） |

**硬规则**

| # | 规则 |
|---|---|
| 1 | 具名**个人**邮箱（如 `firstname.lastname@`）**不得**与角色信箱混同为「官方渠道」；必须随②具名联系人列示并标岗位相关性 |
| 2 | 媒体 / 市场 / 新闻联系人 = **非目标岗**，不得作为 Primary，其邮箱不得作为默认收件渠道 |
| 3 | 四要素缺失时按现状退化（只有角色信箱 → 只写①），**不得为凑齐标签而推测** |
| 4 | 本写法**不改变** 13 个 Internal Key、渠道 4 态判定逻辑与任何评级 |

### 情况 C：查不到具名（**禁止停在此处**）

```
Recommended Contact Role: {三段式 或 二段式}
  No verified contact found
  建议检索路径（下一步去哪里找这个角色 · 不生成任何人名 / 邮箱 / 电话）：
    ① 企业官网「组织 / 管理团队 / 联系我们」页面
    ② 官方公告 / 年报（董事会与高管名单）
    ③ 招投标 / 项目公告中的公开联系人
    ④ 行业协会公开名录
    ⑤ 展会公开参展商资料
    ⑥ LinkedIn 等公开职业信息
```

**情况 C 的硬规则**

| # | 规则 |
|---|---|
| 1 | 「建议检索路径」**只回答"去哪里找"，不回答"是谁"** —— 不生成、不推断、不暗示任何人名 |
| 2 | **禁止**：猜姓名 · 猜邮箱 · 猜电话 · 自动生成邮箱格式（如 `firstname.lastname@`） |
| 3 | **禁止**把第三方聚合站 / 人才库 / 数据聚合站的数据写成 `FACT` 或 `Confirmed`（`evidence-policy.md` 三铁律：FACT 必须有 Source，聚合站属 `Confidence = Low`） |
| 4 | 若某条路径**已确认为不存在**（如官网无团队页），须写明「已确认无此路径」，避免业务员重复劳动 |
| 5 | 路径清单取自本节固定六项，**不得自行增删**（新增路径须先改本文件） |

### 官方联系方式补查阶梯（邮箱检索 · **强制前置动作**）

> **触发条件**：目标**已判定值得开发**（`Sales Conclusion ∈ {建议重点开发, 建议开发, 建议先验证}`），
> 但**尚未取得官方邮箱**（`CONTACT_OFFICIAL_ONLY` / `CONTACT_NONE`）。
> **此时必须先执行本阶梯补查一次**，再决定是否降级为「仅官方渠道」。
> （2026-10-13 立 · 某德国水技术商实测：官网全站页脚含角色邮箱，但被 Cloudflare 保护，markdown 转换首轮遗漏。）

**执行阶梯（按序，命中即可停）**

| 序 | 目标 | 说明 |
|---|---|---|
| ① | **官网首页** | 邮箱常在全站**页脚**，首页即可能命中 |
| ② | **Contact 页面** | `/contact` `/contact-us` `/kontakt` |
| ③ | **Impressum / Imprint** | **德国公司常见法律信息页**，通常必载邮箱 |
| ④ | **官网底部（页脚）** | 与①重叠，但确认页脚是否被 JS 渲染 |
| ⑤ | **官方 PDF** | 年报 / 手册 / 展会资料中的联系页 |

**工具**：`scripts/fetch_official_contacts.py`

```bash
python scripts/fetch_official_contacts.py --domain <域名> --proxy <代理>
python scripts/fetch_official_contacts.py --url <精确页>
```

该工具做三件事：**抓原始 HTML**（非 markdown 转换）、**解码 Cloudflare `data-cfemail`**、提取 `mailto:` 与明文邮箱，
并对每条邮箱输出**来源 URL + 核验日期**，同时标注 `同域 / 角色邮箱 / ⚠️疑似模板`。

**硬规则**

| # | 规则 |
|---|---|
| 1 | **WebFetch 无法呈现 Cloudflare 保护的邮箱** —— 涉及联系方式时**必须抓原始 HTML**（用上面的脚本），不得只靠 WebFetch 的 markdown 结果 |
| 2 | **不得猜测或拼接**邮箱（如 `info@` 试凑、`firstname.lastname@` 构造）；**只记录网页中真实出现（含解码）的邮箱** |
| 3 | **区分三类**：官方公共邮箱（`info@` `contact@`）/ 部门邮箱（`sales@` `ehs@`）/ 疑似个人邮箱 —— 分类须附来源依据 |
| 4 | **找到官方邮箱 ≠ 验证了个人联系人**；`关键联系人` 字段的岗位结论**不因邮箱而改变** |
| 5 | 每条邮箱**必须记录来源 URL 与核验日期** |
| 6 | 走完阶梯仍无命中 → **保留 `CONTACT_OFFICIAL_ONLY`**，并给出**官网联系表单**作为备选；**不得**因补查而放宽证据标准 |
| 7 | 本阶梯**只补联系方式**，**不改任何判断字段**（13 个 Internal Key、`BDD Opportunity`、评级一律不变） |

**注意**：情况 A / A′ / B / B′ / C 中，**岗位角色与服务主体始终输出**。

## 四、接触战略（场景选择）

**依据 `Demand Status` + `Commercial Risk` 的组合决定接触策略。**（矩阵已补齐全部单元格）

| Demand Status | Commercial Risk | 接触策略 |
|---|---|---|
| Confirmed / Strong Signal | Low / Medium | **正常推进**：索要缺失信息，按 Path 选择推进动作 |
| Confirmed / Strong Signal | High | **先收紧再推进**：先确认真实性 / 走保密流程 |
| Confirmed / Strong Signal | **Unknown** | **先确认风险面**：观察索取行为后再决定释放节奏；不因 `Unknown` 视为风险 |
| Potential | Low / Medium | **先补证据**：通过提问确认项目是否存在，暂不投入技术资源 |
| Potential | High | **先补证据 + 收紧**：不释放案例与参数 |
| **Potential** | **Unknown** | **先补证据**：与 `Low/Medium` 同策略。`Unknown` 不作为收紧理由 |
| Weak | 任意（含 Unknown） | **低投入**：只维持接触点，不投技术资源 |
| Unknown | 任意（含 Unknown） | **先确认类型与需求**：保持现有接触点，不主动升级 |

### 三条关键规则

1. **两者可同时成立**（需求很实 + 风险很高）→ **先按高风险收紧，再按强需求推进**，不得二选一。
2. **`Commercial Risk = Unknown` 按中等处理，不按高风险处理。** 这是 V1.1 修复项。
3. **需求强不等于风险低。** 两个维度正交。

> 本文件不输出回复话术。话术属执行范畴，已归档。

## 五、触发信号（定向接触时机）

看到以下信号时定向联系客户，转化率远高于日常跟进。**这些信号同时是 PWE 与 Demand Status 的证据来源。**

| 触发信号 | 接触切入角度 |
|---|---|
| 客户被环保处罚 | "注意到贵司近期的情况，我们在整改类项目上有成熟经验" |
| 客户环评公示 / 技改公示 | "看到贵司 [项目] 的公示，需要废水处理段的技术支持吗" |
| 排放标准加严 / 地方新规 | "新标准对 [指标] 的要求提高了，您现有工艺可能需要评估" |
| 客户新增产线 | "新增产线后废水量和水质可能有变化，建议提前评估" |
| 客户招聘环保工程师 | 说明在有动作 |
| 客户公开披露 ZLD / 提标计划但未闭环 | "注意到贵司仍有厂区在推进 ZLD，是否需要工艺段方案" |
| 伙伴方公布新项目 / 中标 | "看到贵司承接的 [项目]，工艺组合上是否需要补充" |

**说明**：左列为**检索信号**（属背调产物），右列为**接触切入点**。本 Skill 负责识别信号；实际接触与跟进节奏属执行范畴。

## 六、边界（V1.1 明确）

| 不做 | 说明 |
