# 客户类型判定与双路径分流（V1.1）

BDD 业务的客户分六类，**判错类型会导致策略全错**：给工程公司报终端价会被嫌贵，给高校报项目方案会被嫌重，给中间商讲技术故事是白费口舌。

> **V1.1 核心变化：新增双路径分流（End-user Path / Partner Path）。**
> 原因：5 次实跑暴露，同一套判据既用于"废水产生方"又用于"工程 / 集成 / 渠道方"，
> 导致 EPC / 集成商这类**走量主渠道**被按"自身废水"评判，无法被准确表达。

---

## 一、双路径分流（V1.1 新增，优先于一切判定）

**第一步永远是确定 Path。Path 未定 → `BDD Relevance = Unknown`、`Opportunity Type = Unknown`。**

| Path | 客户类型 | Partner Sub-type |
|---|---|---|
| **End-user Path** | 终端业主 | — |
| **Partner Path** | 环保工程公司（EPC） | `EPC` |
| | 系统集成商（成套设备集成，非总包） | `Integrator` |
| | 贸易商 / 中间商 / 分销代理 | `Distributor` |
| | 设计院 · 科研院所高校 · 自有工艺产品线的技术公司 | `Technology Partner` |
| **Undetermined** | Unconfirmed | — |

### 两条路径的判断对象完全不同

| | End-user Path | Partner Path |
|---|---|---|
| 判断对象 | 它自己产生什么废水 | 它能否把 BDD 纳入交付组合 / 渠道 |
| BDD Relevance 依据 | 制造业活动 + PWE / CSD + 窗口信号 | 能力确认 + 技术组合重叠 + 渠道 / 项目信号 |
| 主要机会类型 | `End-user Opportunity` | `EPC / Integration` · `Distribution` · `Technology Partner` |
| **不得做** | 把渠道方按自身废水评判 | **以其自身产生多少废水作为主要判断依据** |

> ⚠️ **Partner Path 不得以"自身废水"为主要判断依据。** 这是 V1.1 的硬规则之一。

---

## 二、判定优先级

按顺序判断，命中即停。**判据必须来自 Evidence，不得凭印象。**

```
① 经营范围 / 登记业务含"环保工程""环境工程""水处理设备""Anlagen zur Wasser- und Abwasserbehandlung"
   → 环保工程公司（EPC）                                  → Partner / EPC
② 高校 / 研究院（.edu / .ac 域名、学校研究所地址、课题组）
   → 科研院所高校                                          → Partner / Technology Partner
③ 名称含"设计院""规划设计""工程咨询"
   → 设计院                                                → Partner / Technology Partner
④ 有实体工厂 + 自身产生废水
   → 终端业主                                              → End-user
⑤ 采购再转售（产品源自第三方品牌 / 独家或授权分销 / 无自有生产）
   → 贸易商 · 中间商 · 分销代理                            → Partner / Distributor
⑥ 提供成套设备集成但非总包（自有产品 + 集成第三方工艺）
   → 系统集成商                                            → Partner / Integrator
⑦ 以上均不成立 / 信息不足
   → Unconfirmed                                           → Undetermined
```

**优先级说明**：
- **① 先于 ④⑤⑥**——若主体同时承接工程又自有工厂，其商业身份以工程为主（但需在 `Company Profile` 注明双重身份）。
- **⑤ 改用"采购再转售"这一实质事实**，不再依赖「参保 < 20 人」的数值门槛（海外主体上该数值普遍无法核实，5 次实跑中 3 次失效）。
- **⑥ 在 ⑤ 之后**——两者都无自有生产，但⑥有技术交付能力，价值类型不同。

**`Unconfirmed` 不是失败，是正确输出。** 信息不足时不得选择"最像"的一类。

## 三、终端业主（End-user Path）

| 项目 | 内容 |
|---|---|
| 定义 | 自己产生废水、自己有排放责任的企业 |
| 识别信号 | 有工厂地址、有产线、行业明确、谈的是"我们的废水" |
| 核心诉求 | 稳定达标、通过验收、不停产、售后有保障 |
| 敏感点 | **最怕运行不稳定和售后找不到人** |
| 推荐联系岗位 | 环保负责人 / 技术总工（详见 `contact-role-map.md`） |
| 推进要点 | **环保处罚 / 整改期限是最强推手** |
| 常见误区 | 直接找老板谈技术往往无效，应先取得环保负责人的技术认可 |

**关键动作**：查环保处罚记录，作为 Demand Status 的证据来源之一。

---

## 四、环保工程公司（EPC · Partner Path）

**定义**：承接废水处理工程总包或分包，采购电极 / 设备集成的公司。**走量主渠道。**

| 项目 | 内容 |
|---|---|
| 识别信号 | 登记业务含环保工程 / 水与废水处理设备；不产生废水；谈的是"某个项目"；要技术参数 |
| 核心诉求 | 方案能通过、成本可控、有厂家背书、能配合投标 |
| 敏感点 | 重视技术参数和响应速度 |
| 推荐联系岗位 | 工艺 / 技术工程师（详见 `contact-role-map.md`） |
| 推进要点 | **配合投标**的能力；提供选型支持与数据支撑 |
| 常见误区 | 把工程公司当业主讲应用故事 |

**反向机会**：查到某项目中标方是工程公司 → **开发中标方比开发业主更快**。

**风险提示**：往往是同时在谈 3~5 家供应商比价的来源。具体定级见 `evidence-policy.md`（**唯一定级来源**）。

---

## 五、系统集成商（Integrator · Partner Path · V1.1 单列）

| 项目 | 内容 |
|---|---|
| 定义 | 有自有产品线，同时集成第三方工艺形成成套交付，但不做工程总包 |
| 识别信号 | 自有产品目录 + 集成第三方工艺的案例；不承担土建；交付为成套设备 / 模块 |
| 核心诉求 | 补齐工艺短板、丰富组合、可对外宣称的工艺完整性 |
| 推荐联系岗位 | 工艺 / 技术负责人 · 产品经理（详见 `contact-role-map.md`） |
| 推进要点 | 定位为**组合补齐**而非替代 |
| 常见误区 | 只谈产品参数，不谈与其现有组合的接口关系 |

**⚠️ 竞争标注**：若其自有工艺与 BDD 目标场景重叠 → 必须标注 `Conflict: 潜在竞争`。

---

## 六、设计院（Technology Partner · Partner Path）

| 项目 | 内容 |
|---|---|
| 识别信号 | 名称含"设计院""规划设计""工程咨询"；邮箱多为机构域名 |
| 核心诉求 | 准确的设备参数用于出图、做概算 |
| 敏感点 | 时间紧（按图审节点）、要参数规范、要厂家资质 |
| 推荐联系岗位 | 工艺设计师（水处理专业）（详见 `contact-role-map.md`） |
| 战略定位 | **不直接采购**，是影响力节点。**最高杠杆的客户类型，常被销售忽视** |
| 推进要点 | 帮设计师把方案做进去 = 锁定后续采购 |
| 常见误区 | 认为设计院"不下单"就不重视 |

---

## 七、科研院所 / 高校（Technology Partner · Partner Path）

| 项目 | 内容 |
|---|---|
| 识别信号 | .edu / .ac 域名；学校或研究所地址；"课题组""实验室""研究" |
| 核心诉求 | 小批量电极做实验、性能稳定、有检测报告、可写论文 |
| 敏感点 | 单价敏感度**低**；更在意参数稳定性与数据可复现 |
| 推荐联系岗位 | 课题负责人（老师）/ 博士生（详见 `contact-role-map.md`） |
| 推进要点 | 快速响应、完整检测报告；长期价值在**论文引用与口碑** |
| 常见误区 | 用项目销售话术对待，过于啰嗦 |

---

## 八、贸易商 / 中间商 / 分销代理（Distributor · Partner Path）

| 项目 | 内容 |
|---|---|
| 识别信号 | 产品源自第三方品牌、独家或授权分销、无自有生产；**一上来就问最低起订量**；不愿透露终端客户 |
| 核心诉求 | 差价；要求独家或区域代理 |
| 敏感点 | 极度价格敏感 |
| 推荐联系岗位 | 负责人 / 总经理（详见 `contact-role-map.md`） |
| 推进要点 | **终端信息确认前不投入技术支持资源** |
| 常见误区 | 为拿到"大单"承诺而给出超常条件 |
| **风险** | ① 套取价格信息 ② 以客户名义套技术方案转售 ③ 无法提供售后，损害品牌 |

> **V1.1 修正**：分销商 **不因"无自有废水"判 `BDD Relevance = Low`**。
> 其机会类型为 `Distribution Opportunity`；判断依据是**渠道覆盖 + 终端客户行业结构 + 是否代理互补水处理产品**。
> `Low` 仅在确证"其技术 / 产品线与 BDD 场景无任何重叠，且不服务工业客户"时才给出。

---

## 九、Unconfirmed（Path Undetermined）

| 项目 | 内容 |
|---|---|
| 触发 | 判定优先级 ①~⑦ 均不成立，或主体信息不足以判定 |
| 下游影响 | `BDD Relevance = Unknown`、`Opportunity Type = Unknown`、`Sales Conclusion = 信息不足，暂缓判断` |
| 推荐联系岗位 | 保持现有接触点，不主动升级（详见 `contact-role-map.md`） |
| 推进要点 | `Next Action` 应为"通过提问确认客户类型" |
| 常见误区 | 强行归为最接近的一类 |

## 十、路径速查矩阵

| | End-user | Partner·EPC | Partner·Integrator | Partner·Distributor | Partner·Tech | Undetermined |
|---|---|---|---|---|---|---|
| 优先级 | 高 | **最高（走量）** | 高 | 低 | 高（杠杆） | 待定 |
| 机会类型 | End-user | EPC / Integration | EPC / Integration | Distribution | Technology Partner | Unknown |
| 核心推手 | 环保处罚 / 整改期限 | 项目中标 | 组合补齐 | 差价 / 代理权 | 规格 / 验证节点 | — |
| 首要动作 | 确认需求证据 | 确认真实性 + 项目 | 谈接口关系 | 索要终端信息 | 进入规格 / 背书 | 确认类型 |
| 商业风险 | 见 `evidence-policy.md` | 见 `evidence-policy.md` | 同上 | 同上 | 同上 | Unknown |

> **本表不含决策周期、价格敏感度、报价路径、技术资料开放口径**——那四列已归档。
> **商业风险一律由 `evidence-policy.md` 定级**，本表不给出类型级先验结论（V1.1 修复了双口径冲突）。

## 十一、组合客户（重要）

| 组合 | 判定 | 处理 |
|---|---|---|
| 工程公司 + 业主一起出现 | 主导方是工程公司 | 按 Partner/EPC 策略，业主在场时控制参数披露 |
| 设计院推荐 + 业主采购 | 双节点 | 先服务设计院定规格，再跟业主 |
| 工程公司自称"我们有个项目"但无中标信息 | 高风险 | 交由 `evidence-policy.md` 定级，不释放技术资料 |
| 主体同时是业主与集成商 | 双重身份 | 在 `Company Profile` 注明；主类型按**当前询盘语境**选择，副类型必须标注 |

## 十二、与其他文件的职责边界

| 文件 | 负责 |
|---|---|
| **本文件** | 客户类型判定 + 双路径分流（Path / Sub-type） |

## 十三、待业务方校准项

- [ ] 六类客户 + Integrator 单列是否与实际一致？需增删？
- [ ] 优先级的 ⑤⑥ 顺序是否符合实际（分销 vs 集成）？
- [ ] 工程公司占业务比重约多少 %？是不是主要走量渠道？
- [ ] 设计院这一渠道目前重视程度如何？
- [ ] 海外主体的登记口径 → 客户类型的映射规则是否需补充？
